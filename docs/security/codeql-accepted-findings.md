# CodeQL 受容記録

`docs/security/codeql-accepted-findings.json` は、`codeql-findings` ゲート（`scripts/tools/check-codeql-sarif.js`）が**落とさずに通す検出**を 1 件ずつ書き出したものである。

## なぜファイルなのか

SARIF には `result.suppressions` という受容の枠がある。ゲートはそのうち `kind: "external"` だけを受け付ける。`external` は code-scanning 側の dismissal から生えるもので、GHAS が無く SARIF の upload が 403 である以上（ADR 0003）、この構成では dismissal が存在しない。

つまり**受容経路は空なのではなく、塞がっている**。それでも出力は `0 accepted suppression(s)` としか言わないので、「誰も受容していない」と「受容する手段が無い」が区別できない。ゲートが受容経路を持たないまま `main` の検出を落とし続ける状態は、赤を常態化させるだけで何も守らない。

`kind: "inSource"`（コード中の抑制コメント）を退けた理由は「ファイルに書くのが悪い」からではなく、**レビューを経ない受容になる**からである。この JSON の 1 エントリは PR の diff として現れ、レビューを経る。コード中の 1 行が誰にも見られずに増える危険は、ここには無い。

## エントリの形

```json
{
  "path": "data/example.html",
  "ruleId": "js/xss-through-dom",
  "count": 1,
  "justification": "なぜこの検出を通してよいのか。空文字は不可。"
}
```

| 項目 | 規則 |
| --- | --- |
| `path` | SARIF の `artifactLocation.uri` を**復号した**形（`%20` ではなく空白）。行番号は書かない |
| `ruleId` | クエリ ID。1 ファイルで複数クエリが出るなら**クエリごとに 1 エントリ** |
| `count` | 受容する件数。1 以上の整数 |
| `justification` | 非空必須。理由の無い受容は記録ではない |

同じ `(path, ruleId)` を 2 行書くと、どちらが何件を消費したのか決められないため structural problem として落ちる。

## 判定規則

**消費数と `count` の一致**で判定する。「`count` 以下なら通す」という上限方式は採らない。上限は**減少方向を吸収する**ためで、5 件が 3 件になっても `3 <= 5` で通り、記録は静かに陳腐化する。多くても少なくても落とす。

行番号を固定しないのは、生成物の再エクスポートで行がずれるだけでゲートが赤くなる設計が、**ドリフトを検出する検査をドリフトを強制する検査へ反転させる**からである。正当な更新でゲートが赤くなり、是正のほうが罰せられる。行を固定しないぶんの緩みは `count` の一致が引き受ける。

受容記録が消費するのは**落とすはずだった検出だけ**である（`security-severity >= 7.0` または `level=error`）。閾値未満の検出まで消費対象にすると、`count` が「受容した件数」ではなく「たまたま一致した件数」になる。

### 解析レジームによる非対称

`pull_request` の run には `incrementalMode: "diff-informed"` が付き、**差分の外にある検出は報告されない**。実測（2026-08-12）:

| run | レジーム | results | うち失格相当 |
| --- | --- | ---: | ---: |
| `main` `64f5954` (push) | full | 11 | 11 |
| PR #143 `bc9e53b` | diff-informed | 6 | 6 |
| PR #157 `aaa98a7` | diff-informed | 5 | 5 |

差の 5 件は差分外の `data/…html` である。したがって PR run の「0 件」は「無い」ではなく「**見ていない**」を含む。

この事実から、一致判定を次のように非対称にしている。

| ずれ | full run | diff-informed run |
| --- | --- | --- |
| 消費 > `count`（超過） | **落ちる** | **落ちる** |
| 消費 < `count`（不足） | **落ちる**（記録が陳腐化している） | 落ちない |

不足を diff-informed で落とさないのは、**差分外を見ていない以上、不足は陳腐化の証拠にならない**ためである。厳密一致をそのまま適用すると、html に触れない PR は必ず「宣言 4 / 消費 0」で赤くなり、ゲートは自分の PR を落とす。超過を両方で落とすのは、見えている以上「多い」ことは確実に言えるからである。**片側だけが観測可能だから、判定も片側だけ厳しい。**

ゲートは合格・不合格のいずれでもレジームを出力する。これを書かなければ、diff-informed の「finding 0 件」が full の「finding 0 件」と同じ文字列で出る。

## 追加・削除の手順

1. 検出が**本当に修正できない／修正すべきでない**ことを確かめる。修正できるなら修正する。受容記録は修正の代わりではない。
2. `main` の push run（full）で出た SARIF を基準に `path` / `ruleId` / 件数を数える。PR run の数字は差分外を含まないため基準にならない。
3. エントリを追加し、`justification` に**何が変われば見直すか**まで書く。
4. 検出が消えたら、その PR でエントリも減らす。減らし忘れは次の full run で「宣言 N / 消費 M」として落ちる。

## この記録が守らないもの

- ゲートを required status check にすること自体はこの記録の範囲外である。branch protection の変更は §17 の Approval PR を要する。
- `MAX_ACCEPTED_SUPPRESSIONS`（SARIF 内抑制の予算 0）は据え置きである。この記録は SARIF 内抑制を増やさない。
